The app is the ordinary half. Workouts are logged on a phone against a library of about 150 seeded exercises, with last session's numbers in grey behind the inputs, double-progression pre-fill, supersets, a plate calculator and a rest timer. Weights are stored in kilograms and converted only for display, so switching units never rewrites history, and personal records are recomputed from the sets themselves inside the same mutation that saves a set rather than being maintained as a separate tally that could drift. The in-progress workout lives in `localStorage` and syncs when the network returns, which is the right shape for a thing used in a basement gym with no signal.

The unusual half is that Claude can use it. `lib/mcp-server.ts` registers thirteen tools against a Convex backend — eight that read (exercises, programs, routines, workout history, progress summaries, bodyweight) and five that write (create an exercise, a routine, a program, log a bodyweight, update a routine). None of them deletes, and that is a stated design rule rather than an omission: the header of `convex/mcp.ts` says logged history cannot be touched from the connector, and `update_routine`, the only write flagged destructive, archives the previous version and returns the new id instead of overwriting. A test asserts the absence negatively — no tool name matches `/delete|remove/` — so the rule fails the build rather than eroding quietly.

The transport is stateless Streamable HTTP in the literal sense: `sessionIdGenerator: undefined`, a fresh server per request, `server.close()` in a `finally`, and `GET` and `DELETE` answered with 405 and an `Allow: POST`, because there is no standalone event stream and no session to delete. Tokens are 32 random bytes — 256 bits — base64url-encoded behind a `gt_` prefix, shown once and stored only as a SHA-256 hex digest; the table has no plaintext column. Verification hashes the presented token and looks it up by index, refusing anything revoked or out of scope, and revocation is a soft delete the profile screen exposes behind a confirm. The listing endpoint is asserted never to serialize the hash.

Tracing is where the token problem resurfaces, and the answer is the part worth keeping. Langfuse is registered as the only span processor on the tracer provider, and `shouldExportSpan` admits a span only if its name starts with `tool:` — the comment gives the reason plainly, that Next.js and HTTP spans carry the request URL and the request URL can hold the connector token. Each tool call is forced onto its own root context so it never arrives as a child of the unexported request span, and a regex masking anything shaped like a token runs over the payload as a backstop. The test plants a real token in a fake request span's `http.url`, runs two tool calls through the processor, and asserts both that only the two `tool:` spans were exported and that the serialized export contains no `gt_` anywhere. A sibling test checks the tool results are byte-identical with tracing on and off.

The iOS shell is a thin Capacitor WebView over the deployed site — `ios/www/index.html` is three lines and says so — carrying one thing the web cannot do, a Live Activity that keeps the rest timer counting on the lock screen. It is installed by sideloading a built `.ipa` through SideStore rather than TestFlight, which costs nothing and no Apple developer account, and the twelve commits on 2026-10-27 that got it working are mostly about safe-area insets, over-scroll colour and where to register the plugin on the scene's bridge controller.
